# Extraction plan (internal)

Status: 2026-11-19. **This directory is not part of the public repository.** It is removed
before the public first commit (checklist, section 7). It describes how code moves from the
private predecessor into Foundry and how the predecessor later adopts Foundry.

This file contains no personal names, hostnames or home paths on purpose. Where the
predecessor's code contains them, this file says "household-specific" and gives the
location, not the content.

"Predecessor" means the private monorepo Foundry is extracted from. Paths below are
relative to its root.

## 1. Rules

1. **Specification first, porting second.** Foundry packages are written to the public
   specification. Predecessor code is a reference for behaviour and a source of tested
   logic, never something to copy as a directory.
2. **File by file, through a gate.** Each ported file is copied into a clean staging tree,
   edited, scanned, and only then added to Foundry. No `git mv`, no history, no bulk copy.
3. **Allowlist, not blocklist.** A file reaches Foundry only if this plan names it. A file
   not named here is not ported.
4. **No fixtures cross over.** Every Foundry fixture is generated by a script written for
   Foundry. This includes test data, benchmark question sets and example configuration.
5. **The predecessor is not edited by this work.** Its migration (section 6) needs the
   owner's explicit approval and its own plan.

## 3. What must change in anything that is ported

| Item | Change |
|---|---|
| Derivation labels and format magic | New labels under `foundry/…` and new magic. Nothing written by Foundry is readable by the predecessor's code or the reverse. |
| Person identifiers used as code values | The predecessor uses given names as partition values, source names and tier names. In Foundry these are `me`, `partner`, `child`, `other` plus user-chosen display names stored only in the vault. |
| Source ids | Generic, of the form `<provider>/<product>`. No source id names a person. |
| Paths, hostnames, service names | None. Foundry has no deployment target baked in. |
| Comments and test names | Rewritten. Comments in the predecessor refer to people and incidents. |
| Licence headers | None needed; the repository licence covers the files. Confirm every ported file was written for the predecessor and not copied from a third party. |

## 4. The scrub gate

Run for every ported file, in the staging tree, before it is added to Foundry:

1. Secret scan with the standard rules **and** the private pattern file that lists the
   household's names, hostnames and account identifiers. That pattern file lives outside
   every repository and is never copied into Foundry.
   **Known gap, found 2026-11-19:** that pattern file currently skips every Markdown file
   (it has an allowlist for `.md`). For Foundry it must be run with that allowlist removed,
   or documents are not scanned at all. The scan recorded in section 8 was run that way.
2. Search for home-directory paths, private network addresses, device names and email addresses.
3. Read the file top to bottom once. A scanner does not catch a nickname or a described event.
4. Run the file's tests against synthetic fixtures only.

Run for the whole tree, in CI, on every push: the standard secret scan and a generic
identifier scan (home paths, email addresses, private network addresses). The private
pattern file cannot run in public CI, so the owner runs it locally before each release,
against the tree **and** against every release archive.

## 5. Order

| Step | What | When |
|---|---|---|
| 1 | Nothing is ported for Step Zero. It is written new. | Phase 0 |
| 2 | Record encryption and manifests written to specification, with the predecessor's crypto tests used as a checklist | V-1 to V-3 |
| 3 | Generic index tables and search ported through the gate | V-4 |
| 4 | Contacts parser ported; calendar and mail written new | V-5 |
| 5 | Generic sensitivity rules ported | P-1 |
| 6 | Location parser ported | X-1 |

## 6. Later: the predecessor adopts Foundry

Not started. Needs the owner's approval before any change to the predecessor.

1. The predecessor depends on Foundry packages at a pinned version.
2. One-time migration of its live databank: read each stored item with the old code,
   append it to a new Foundry vault under generic profiles, verify counts and hashes, keep
   the old databank read-only until a restore drill passes on the new one.
3. Household-specific rules, sources and names become configuration in the new vault.
4. The old storage code is deleted from the predecessor only after step 2 has been verified twice.
5. Rewriting the predecessor's pushed history to remove names is a separate question. It
   needs a force push and therefore the owner's explicit confirmation. Nothing in Foundry depends on it.

## 7. Checklist before the public first commit

- [ ] `docs/internal/` is absent from the export.
- [ ] The export is made from an allowlist into an empty directory; no `.git` is copied.
- [ ] Standard secret scan passes on the export.
- [ ] Private pattern scan passes on the export and on every release archive.
- [ ] No fixture, log, index, vault, keyring or `.env` file is in the export.
- [ ] One human read of every document for names, places and described events.
- [ ] Product name and package scope chosen (Decisions Q-2).
- [ ] The owner creates the public repository and makes the single first commit.
